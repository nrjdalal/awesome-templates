| Admin neutral-mono restyle — and the brand palette that never applied | #365 (PRs #366, #367) | The restyle (desaturated Tailwind zinc ramp, one blue accent, `8px`/`6px` rounding, hairline borders, flat login backdrop, `36px` rows, striping off, system font stack replacing a bundled 1.29 MB woff2) was the *stated* job. The real finding: **the `--q-*` half of the token system had never taken effect.** NiceGUI writes its brand palette as an **inline style on `<body>`**, which outranks every stylesheet rule regardless of specificity, so `theme.py` declaring `--q-*` in `:root` was inert from #193 through #235 — measured on `main` as `rootVar #2563eb` / `bodyVar #5898d4`. Every button, badge and `text-primary` rendered NiceGUI's defaults (pale blue, **teal** secondary, **purple** accent, **cyan** info) beside the `--admin-*` greys, i.e. a third palette on screen. That, not the `AdminColors` ramp-mixing the issue was filed for, is the larger reason admin colours never sat right. Fixed by emitting `_BRAND_TOKENS` under `body` with `!important` (which does outrank a normal inline declaration) — verified against the live page, not inferred. `--q-dark`/`--q-dark-page` are set too so Quasar's own dark menus/dialogs land on the zinc ladder. Two more defects surfaced only because a light/dark **screenshot pass** was run, and neither was reachable by unit test: the AG Grid body kept the quartz surface while cards used `--admin-surface`, so pinning *only* `--ag-odd-row-background-color` to kill striping made striping reappear **inverted**; and `.admin-drawer .q-icon` (0,2,0) outranked `.admin-text-muted` (0,1,0), so muting inactive nav icons applied to nothing. | Error Notification Channel Routing | #286 (PR #313), #315 (PR #319) | Adds optional severity-based channel routing on top of #17/#310. `NOTIFICATION_WARNING_THRESHOLD` is the **sole switch** — set below `NOTIFICATION_SEVERITY_THRESHOLD` it lowers the alerting floor to `min(severity, warning)` (`ErrorNotifier._effective_min_threshold`) and `NotificationRouter.resolve()` picks the tier client (`None` = do-not-dispatch). `NOTIFICATION_CRITICAL_WEBHOOK_URL` / `NOTIFICATION_WARNING_WEBHOOK_URL` are per-tier overrides that each fall back to the single provider webhook; they do **not** enable routing and are rejected at boot without the threshold (#315 — that combination previously booted and silently sent every alert to the base webhook). Cooldown key becomes `{tier}:{error_code}`, composing with #310's task prefix to `{tier}:{task_name}:{error_code}` — a bare key let a warning-tier 4xx mute a critical-tier 5xx, reachable with no subclass since `BaseCustomException` takes both args per instance. `CoreContainer` now holds four notification Selectors; the three client ones share **one** `_noop_notification_client` Singleton so the disabled path still logs `notification_client_disabled` exactly once (pinned by test), while `notification_router` declares `providers.Object(None)` on its `disabled` branch and therefore resolves to `None`. External contributor; 3 maintainer review rounds. |
| Worker Error Notifications | #310 | Extends error-notification dispatch to Taskiq task failures via `TaskFailureNotificationMiddleware` (`_core/infrastructure/notification/taskiq_middleware.py`), closing the surface #311 documented as a coverage limit. No new env vars — reuses `NOTIFICATION_*`. Worker specifics: severity is synthesised (`BaseCustomException` keeps its `status_code`, else 500) so `NOTIFICATION_SEVERITY_THRESHOLD` still applies; the cooldown key is scoped `{task_name}:{error_code}` so one noisy task cannot mute the rest; alerts fire once per incident on the terminal failure (permanent errors immediately, retryable ones after the last attempt). Middleware registration order is load-bearing and pinned by tests — taskiq runs `on_error` over `reversed(middlewares)` and the retry middleware mutates `_retries` in place. NiceGUI admin exceptions resolved as an explicit **non-goal** (operator-attended). Also closes #311's deferred R4: negative tests now pin that 422 / `HTTPException` never dispatch. |
| Error Notification Webhooks (contributor) | #17 (PR #304) | Adds optional error-notification core infra — the **first `src/` runtime feature after v0.9.0**. Slack/Discord webhook adapters + `NoopNotificationClient` fallback behind the ADR 042 Protocol + Selector pattern (`NOTIFICATION_PROVIDER` + matching webhook URL enable it; `BaseNotificationProtocol` in `_core/domain/protocols/`). `ErrorNotifier` gates by `NOTIFICATION_SEVERITY_THRESHOLD` (default 500) + a per-process, per-error_code `NOTIFICATION_COOLDOWN_SECONDS` (default 60) and dispatches fire-and-forget (`asyncio.create_task` — never awaited in the request path; send failures logged `exc_type`-only so the secret webhook URL never reaches logs). Hooked into `custom_exception_handler` + `generic_exception_handler` via `app.state.container` at runtime (no infra import in the exceptions module; dispatch never raises into the response path). Adapters POST via the shared `HttpClient` and never JSON-parse webhook responses (Slack success body is plain-text `ok`, Discord returns `204`). Settings validation follows the existing partial-config-group pattern (unknown provider / missing webhook URL rejected at boot, tested). Channel routing deferred to #286 (shipped in PR #313). 3-round review (Codex bot + 2 protocol rounds; all finding keys FIXED at merge). |
